# S3 · 相机取景 + ML Kit 中文 OCR 设计（设计先行 · 待确认）

> 本文是 **S3 编码前** 的完整设计文档，覆盖 CameraX 取景、相机权限、ML Kit 中文 OCR、解析规则、稳定结果判定、异常状态与 S3/S4 边界。
> **在本文通过审阅并获得确认前，不开始编码。**
> 设计依据：`DESIGN_SYSTEM.md`（Token/组件）、`UI_GUIDELINES.md`（纪律）、`UI_REVIEW.md`（逐页决策）、`S1_ENTITY_DESIGN.md`（数据模型）、`S2_UI_DESIGN.md`（首页/列表的入口与确认前置）。

---

## 0. 设计意图（一句话）

> 打开相机，对准药盒，稳定识别包装文字，但**不自动下结论、不自动落库**；OCR 只产出可编辑候选值，真正入库必须等 S4 用户确认。

S3 是“采集与识别层”，不是“判断层”，更不是“医疗建议层”。

---

## 1. S3 的职责边界

### 1.1 S3 只负责
- 相机预览与取景。
- 相机权限申请、拒绝、永久拒绝的引导。
- 本地 CameraX 帧分析。
- ML Kit 中文文字识别。
- OCR 原始文本采集、稳定结果判定、节流与防抖。
- 把识别文本解析为**药品事实字段候选值**。
- 把候选值带入 S4 的确认页。
- OCR 失败时引导手动录入。

### 1.2 S3 不负责
- 不保存 Medicine。
- 不写入 `usageNote / contraindicationNote / precautionNote / userNote`。
- 不做疾病判断、用药推荐、剂量计算、相互作用判断。
- 不调用任何外部 API、云端 AI、LLM。
- 不把 OCR 结果直接视为事实。
- 不替代 S4 的字段确认。

### 1.3 S4 才负责
- 用户逐字段确认 / 编辑 OCR 结果。
- 事实字段最终落库。
- 处理重复药品、补录空字段、补录位置、补录照片等确认操作。

## 2. 设计总原则

### 2.1 本地优先
- 全流程只用 Android 本地能力。
- CameraX + ML Kit 中文文字识别均在本地运行。
- 无服务器、无登录、无 API Key。

### 2.2 OCR 只识别文字，不解释医疗内容
- 识别目标仅限药盒 / 说明书 / 包装上的文字。
- 结果只被解释成“名称、规格、厂家、批号、日期”的候选值。
- 任何“该不该吃”“能不能吃”“该吃多少”的内容都不在范围内。

### 2.3 结果必须可编辑
- OCR 不可靠，必须默认进入确认流程。
- 任何自动解析都只是“候选建议”，不是事实。
- OCR 失败后，手动录入仍然是主路径之一。

### 2.4 UI 克制
- 仍沿用暖纸、鼠尾草绿、系统中文字体、发丝线、低装饰密度。
- 扫描页不做“科技感相机壳”“扫描框光效”“AI 识别动画”。
- 识别中、失败、权限态都用人话说清楚。

## 3. S3 页面与流转

### 3.1 页面清单
- `ScanScreen`：相机取景页。
- `OcrProcessingState`：识别中覆盖态。
- `OcrResultPreview`：OCR 初步结果预览态（可视上仍可属于 ScanScreen 的结果层）。
- `AppPermissionState`：相机权限态。
- `AppOcrFailedState`：识别失败态。
- `OcrConfirmScreen`：S4 确认页，S3 只负责把候选值传过去。

### 3.2 推荐流转
1. 从首页“扫描药品”进入 `ScanScreen`。
2. 先检查相机权限。
3. 有权限则打开 CameraX 预览。
4. 用户对准药盒后触发分析。
5. 帧分析得到 OCR 原始文本。
6. 经过节流 / 稳定判定 / 解析规则后，形成候选字段。
7. 若候选足够稳定，进入 S4 确认页。
8. 若识别不成功，显示失败态并保留手动录入入口。

### 3.3 不推荐流转
- 不要直接从 OCR 写入数据库。
- 不要让 OCR 结果跳过确认页。
- 不要在扫描页上做复杂编辑。

## 4. CameraX 取景页完整 UI/UX

### 4.1 页面目标
打开相机后，用户能立刻知道：
- 镜头已经开启。
- 应该把药盒放在画面中央。
- 当前是在拍摄“药盒文字”，不是“随手拍照”。
- 有问题时，应该怎么继续。

### 4.2 页面结构

```
┌────────────────────────────────────┐
│ AppTopBar                           │  ← 标题 + 取消 + 可选闪光灯
├────────────────────────────────────┤
│                                    │
│   全屏 CameraX Preview             │
│   - 预览占主体                     │
│   - 可叠加极轻遮罩                 │
│   - 不做花哨扫描框                 │
│                                    │
│        取景提示文字                │  ← “把药盒正面放进画面”
│                                    │
│   底部操作区                       │
│   - 重新拍摄 / 识别中状态 / 手动录入│
└────────────────────────────────────┘
```

### 4.3 UI 规则
- 预览区占屏幕主体，尽量不被卡片、说明块切碎。
- 顶部动作只保留必要项：取消、可选闪光灯、可选相册入口（若后续评估需要）。
- 底部操作区只提供当前阶段最关键的动作，不堆按钮。
- 取景提示只放一行到两行，保持安静。
- 不用复杂扫描网格，不做“AI 识别边框发光”。
- 需要时可用极轻的半透明遮罩帮助聚焦，但不遮挡关键信息。

### 4.4 推荐文案
- 标题：`扫描药品`
- 提示：`把药盒正面放进画面，尽量让文字清楚。`
- 次级提示：`支持识别名称、规格、厂家、批号和日期。`
- 取消：`取消`

### 4.5 交互
- 用户可手动触发识别，也可在画面稳定时自动触发分析。
- 识别时相机预览继续运行，不要切黑屏。
- 识别结果出现后，若用户继续移动镜头，允许重新采样，不要立即锁死结果。
- 如果识别稳定，可以自动进入 S4；如果稳定性不足，停留在结果预览层，等待用户确认是否继续。

## 5. 相机权限状态设计

### 5.1 状态分类
- 未申请。
- 已允许。
- 已拒绝但可再次申请。
- 永久拒绝（不再弹系统授权框）。

### 5.2 权限态 UI
沿用 `AppPermissionState` 的克制风格：
- 图标可用相机图标，但不放大到装饰级别。
- 一句解释为什么需要权限。
- 一个主按钮引导去授权。
- 永久拒绝时，增加“去系统设置”入口。

### 5.3 文案建议
- 未授权：`药箱管家需要相机来扫描药盒。`
- 授权按钮：`允许使用相机`
- 永久拒绝：`相机权限已关闭，请到系统设置里重新开启。`
- 设置按钮：`去系统设置`
- 备用路径：`我先手动录入`

### 5.4 设计要求
- 拒绝后仍然保留 App 的可用路径，不阻断整个流程。
- 永久拒绝时，不反复弹窗骚扰。
- 权限态不是错误态，不用红底恐慌。

## 6. OCR 状态设计

### 6.1 OCR 的四个核心状态
- 准备中
- 识别中
- 识别成功
- 识别失败

### 6.2 准备中
用于相机刚打开、分析器未就绪、模型或纹理尚未准备完成。

UI：
- 细 spinner 或中性文字。
- 文案：`正在准备识别…`
- 不要让用户以为卡死。

### 6.3 识别中
用于帧已进入分析，模型正在输出文字。

UI：
- 轻量 loading 覆盖，不遮住整个相机。
- 文案：`正在识别药盒上的文字…`
- 不要使用夸张进度条，不要一直跳动。

### 6.4 识别成功
识别成功不等于落库成功。

UI：
- 进入“结果预览层”或直接跳转 S4。
- 文案：`已识别到文字，继续确认即可保存。`
- 仍然保留“重新识别”和“手动录入”。

### 6.5 识别失败
失败包括：文字太少、太模糊、画面抖动、反光、文字方向异常、帧质量不足、模型无有效输出。

UI：
- 中性失败态。
- 文案：`没看清包装上的字。`
- 说明：`你可以换个角度再试，或者直接手动填写。`
- 主路径保留：`手动录入`

### 6.6 不建议的文案
- 不要写“识别错误，请重试”（过于生硬）。
- 不要写“AI 识别失败”（不符合产品定位）。
- 不要写“系统忙，请稍后”。

## 7. OCR 原始文本 → 药品事实字段候选值的解析规则

> 这一层只做“文本归类”和“候选提取”，不做医疗推理，不做事实确认。

### 7.1 输入
- ML Kit 输出的原始文本块。
- 每块可能带有行、块、语言方向信息。
- S3 仅消费文本，不依赖图片上传或云端服务。

### 7.2 输出
输出一组候选字段：
- `nameCandidate`
- `specificationCandidate`
- `manufacturerCandidate`
- `batchNoCandidate`
- `productionDateCandidate`
- `expiryDateCandidate`
- `confidence` / `sourceLines`

### 7.3 基本策略
1. 优先从标题行 / 大字号行里找药名候选。
2. 从包含单位、规格格式、数字+单位模式的行里找规格候选。
3. 从带有“厂家、生产企业、委托企业、企业名称、制造商”等关键词的行里找厂家候选。
4. 从带有“批号、批次、Lot、Lot No、Batch No”等关键词的行里找批号候选。
5. 从带有“生产日期、生产日期：、MFG、制造日期”等关键词的行里找生产日期候选。
6. 从带有“有效期至、Exp、EXP、截止日期、有效期至：”等关键词的行里找有效期候选。
7. 同一字段允许多个候选，S4 再让用户确认。

### 7.4 置信度原则
- 不是“自动猜一个最像的答案”，而是“给出最稳的候选集合”。
- 模糊时宁可少提，不要强行填错。
- 低置信度字段应显式标记“待确认”。

### 7.5 行级优先级建议
- 药名：标题行、最短且高频词少的行优先。
- 规格：与药名同行或相邻行优先。
- 厂家：包含厂字、企业字、生产字的行优先。
- 批号：明确标记批号的行优先。
- 日期：明确日期格式的行优先。

### 7.6 不做的事
- 不做药理推断。
- 不从药名推断适应症。
- 不从包装文案推断用法用量。
- 不自动补全不存在的字段。

## 8. 字段提取策略

### 8.1 药品名称
目标：尽可能提取包装正面 / 说明书标题中的真实药名。

策略：
- 优先整行匹配，避免只拿到局部片段。
- 排除明显的品牌宣传语、批准文号、广告语。
- 若同页出现多个候选，保留多个给 S4 选择。

### 8.2 规格
常见模式：
- `0.3g*20片`
- `10ml*5支`
- `9g*10袋`
- `100mg`

策略：
- 识别数字 + 单位 + 乘号/星号/× 的组合。
- 保留原始书写样式，S4 再可编辑。
- 不做单位换算。

### 8.3 厂家
常见关键词：
- 生产企业
- 生产厂家
- 企业名称
- 制造商
- 委托生产

策略：
- 从关键词后的整行或邻近行提取。
- 如果 OCR 拆成多行，允许拼接相邻行。
- 保留原文，不做公司标准化。

### 8.4 批号
常见关键词：
- 批号
- Lot
- Batch No
- 批次

策略：
- 仅把明确有批号语义的文本纳入候选。
- 避免把批准文号误当批号。

### 8.5 生产日期
常见形式：
- `2026-03-15`
- `2026.03`
- `2026年03月`

策略：
- 识别成 `ApproxDate` 候选。
- 若只有年月，保留 `YEAR_MONTH` 精度。
- 不要自动补日。

### 8.6 有效期
常见形式：
- `有效期至 2028-03`
- `EXP 2028-03-15`
- `2028年03月`

策略：
- 同样识别成 `ApproxDate` 候选。
- 只记日期，不做“还剩多少天”的医疗解释。
- 保持原始精度。

## 9. ApproxDate 的精度保护

### 9.1 核心要求
- `2028-03` 必须保持为年月精度。
- OCR 不得把 `2028-03` 偷偷变成 `2028-03-01`。
- S3 只负责提取候选，不做强制精度升级。

### 9.2 精度规则
- OCR 看到年-月格式 → `YEAR_MONTH`。
- OCR 看到年-月-日格式 → `FULL_DATE`。
- 缺少日时，保持年月，不补日。
- S4 确认页应显示原始精度。

### 9.3 展示规则
- `2028-03` 显示为 `2028年3月`。
- `2028-03-15` 显示为 `2028年3月15日`。
- 不显示 `2028年3月1日` 作为年月代替。

### 9.4 错误示范
- 任何“为了方便比较先补成月初”的做法都不允许。
- 任何“显示时统一补日”的做法都不允许。

## 10. OCR 结果与 Medicine 事实字段的关系

### 10.1 可转入 S4 的事实字段
- name
- specification
- manufacturer
- batchNo
- productionDate
- expiryDate
- photoPath（如有）
- locationId（可由用户之后指定）

### 10.2 明确不转入的字段
- `usageNote`
- `contraindicationNote`
- `precautionNote`
- `userNote`

### 10.3 原则
- OCR 只给“包装上可见的客观事实”候选。
- 用户备注类字段一律留给用户手动输入。
- 即使 OCR 识别到说明书上的注意事项，也不能转成用户备注的默认值。

## 11. 连续帧 OCR 的节流、防抖与稳定结果判定

### 11.1 为什么需要
CameraX `ImageAnalysis` 会高频推送帧，直接每帧 OCR 会：
- 过热。
- 掉帧。
- 重复识别同一画面。
- 结果抖动。

### 11.2 节流策略
- 分析帧限流，不必处理每一帧。
- 例如只在固定间隔或固定间距帧数上触发 OCR。
- 当识别耗时较高时，后续帧直接丢弃或合并。

### 11.3 防抖策略
- 识别结果变化时，不立即判定“稳定”。
- 需要连续若干次得到相同或高度相似的候选。
- 对名称、规格、厂家、日期分别做稳定性判断。

### 11.4 稳定结果判定
建议满足以下条件再进入 S4：
- 药名候选连续多次一致，或相似度足够高。
- 规格 / 日期 / 厂家中至少部分字段达到可信阈值。
- 最近几帧文本的核心字段不再剧烈变化。

### 11.5 不建议的策略
- 不要一识别到文字就强跳确认页。
- 不要在每帧都刷新整个 UI。
- 不要用动画掩盖结果抖动。

## 12. CameraX 生命周期与资源释放

### 12.1 绑定方式
- 预览与分析器跟随 `LifecycleOwner`。
- 进入扫描页绑定。
- 离开页面解绑。

### 12.2 资源释放
- 页面退出立即释放相机资源。
- 避免前后台切换后继续占用镜头。
- 识别中若页面退出，必须取消未完成分析。

### 12.3 重建策略
- 配置变化 / 旋转后重新绑定预览，不保留旧的无效引用。
- 如果分析器被暂停，恢复后重新开启。

### 12.4 异常处理
- 相机设备暂时不可用时，进入错误态而非空白。
- 资源释放失败也要兜底，避免黑屏卡死。

## 13. 低端 Android 手机的性能策略

### 13.1 约束
家庭用户可能使用入门机型，因此 S3 不能只在高端机上流畅。

### 13.2 性能策略
- 降低 OCR 触发频率。
- 必要时降低分析分辨率。
- 控制帧处理队列长度。
- 使用单线程或轻量线程池处理 OCR。
- 识别结果只在“变化明显”时更新 UI。

### 13.3 体验策略
- 相机预览优先流畅。
- OCR 次之。
- UI 不要频繁重组。
- 若设备性能过低，允许用户手动拍摄后再识别，而不是实时连续分析。

### 13.4 不做的事
- 不上云端识别兜底。
- 不调用外部服务补速度。
- 不加入与任务无关的重特效。

## 14. 异常状态设计

### 14.1 无权限
- 显示相机权限说明。
- 引导授权。
- 保留手动录入。

### 14.2 永久拒绝
- 显示去系统设置按钮。
- 不再重复弹系统框。

### 14.3 无结果
- 文案：`没看清包装上的字。`
- 说明：`你可以换个角度再试，或者直接手动填写。`

### 14.4 模糊
- 提示靠近一点、保持稳定、对准正面。
- 不用“识别率低”这种机器口吻。

### 14.5 文字太小
- 提示“把药盒放近一点”。
- 不做夸张放大框。

### 14.6 旋转 / 横竖屏切换
- 重新绑定相机。
- 保留当前识别状态或恢复到准备中。

### 14.7 暂时失败
- 保留重试和手动录入。
- 不把失败当终点。

## 15. 反 AI UI 审美设计

### 15.1 视觉要求
- 暖纸背景。
- 系统中文字体。
- 单一鼠尾草绿作为品牌强调。
- 发丝分隔线。
- 低密度装饰。
- 相机页以取景画面为主，不做科技壳。

### 15.2 禁止项
- AI 紫。
- 渐变。
- 玻璃拟态。
- 霓虹。
- 粒子与发光。
- 大圆角卡片堆叠。
- 过度图标化。
- 营销腔文案。

### 15.3 页面气质
- 真实工具感。
- 安静。
- 能看清。
- 不抢眼。
- 不像演示稿。

### 15.4 设计自检
1. 第一眼像 AI Demo 吗？
2. 相机页像拍照工具还是像装饰页面？
3. OCR 失败时有没有把用户卡死？
4. 文案是不是说人话？
5. 是否把结果夸大成事实？
6. 是否有不必要的卡片墙？
7. 是否有不必要的科技效果？
8. 是否能删掉 10% 的视觉元素？
9. 是否保留了手动录入的主路径？
10. 隐去项目名后，是否仍像一个成熟工具？

目标：**≥ 8/10**。

## 16. S3 与 S4 的边界

### 16.1 S3 结束点
- CameraX 可以打开。
- OCR 可以识别本地文字。
- 结果可以被解析为候选字段。
- 用户可以看见失败态并选择手动录入。
- 可以把候选值带入 S4。

### 16.2 S4 开始点
- 用户确认 OCR 候选字段。
- 用户编辑字段。
- 用户决定是否保存。
- 用户决定是否创建新药品或更新已有药品。
- 字段最终落库。

### 16.3 绝不跨越的线
- S3 不自动写入 Medicine。
- S3 不自动补全用户备注。
- S3 不自动给出医疗解释。
- S3 不自动作“是否可靠”的最终判断。

## 18. 设计结论

- S3 只做“看见文字”和“生成候选”，不做事实确认。

- 结果必须通过 S4 确认后才能进入数据库。
